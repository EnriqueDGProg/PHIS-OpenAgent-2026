All four exact images referenced by the active Compose services were already present locally: `postgres:16-alpine`, `zetaris-ndp-driver`, `zetaris-ndp-api` and `zetaris-new-ui` at the bundle's pinned hackathon tags. `docker compose up -d --no-build --pull never` created the stack without another pull or build. `postgres`, `driver`, `api` and `ui` reported `running/healthy`. The one-shot `init` exited 0; `bootstrap` was still loading the vendor's sample data at the health snapshot. That sample-data job was not used for this proof.

The active Compose publishes UI `3000`, API `8888/8889`, JDBC `10000`, Spark UI `4040` and dynamic catalog/Postgres ports only on `127.0.0.1`. The TLS/public profile was inactive. The existing 2 GB driver heap, 2 driver cores and 1 GB API heap were unchanged; no memory adjustment was needed.

The only staged dataset was a 156-row fictional CSV, generated by this repository and explicitly marked synthetic. Host and in-container SHA-256 both equalled `7f97f660600fa2fd592b70a707ddf4db94420b4af6ee3ab281b90ddbb61641a5`. It was copied into the official shared `customer-data` volume at `/home/zetaris/customer-data/shared/phis_synthetic_observations.csv`; the running driver could read it.
